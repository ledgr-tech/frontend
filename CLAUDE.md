## Workflow

- Work on `develop`, never commit directly to `main`. Non-trivial feature work should happen in an isolated git worktree under `.worktrees/` (already gitignored) on its own branch, merged/PR'd back into `develop` when done.
- Before committing: `npm run test && npm run lint && npm run build`. Running `build` (not just `test`) matters — see the route-group typo note in `AGENTS.md`; it's the kind of bug tests alone won't catch.
- Real screen copy/data (landing page sections, product terminology, etc.) should come from the Claude Design export for this project, not be invented — check for the source file before writing placeholder text.

## Backend status

- **The upload → conciliation flow is real.** `lib/backend.ts` is the only place that talks to the FastAPI backend (`LEDGR_API_URL`), always server-side, always with a `Authorization: Bearer <jwt>` built from the session cookie. Screens reach it through Server Actions (`app/(app)/conciliacoes/acoes.ts`), never with `fetch` from the browser. The one exception is a file: the CSV export can't come back through a Server Action, so `app/api/conciliacoes/[id]/exportar/route.ts` is a Route Handler that calls `baixarDoBackend` and passes the bytes through untouched (decoding as text drops the UTF-8 BOM, and Excel then breaks the accents).
- **Session is NextAuth** (`auth.ts` at the root), with `jwt.encode`/`decode` replaced so the cookie *is* the HS256 token the backend validates — see `lib/token.ts` for the claim contract (including `auth_time`, copied from the `POST /login` answer at login and kept on every renewal, never computed here: backend #75 rejects tokens without it and counts the 7 days from it) and `docs/superpowers/specs/2026-09-22-integracao-backend-design.md` for why.
- **Login and signup are real.** `authorize` calls `POST /login` (`lib/login.ts`) and the signup calls `POST /register` (`app/(auth)/acoes.ts`). Leaving the company step, the signup asks `POST /register/verificar` (backend #80) whether the e-mail and the CNPJ are free; the route takes both together, so the check waits for the CNPJ, and with no answer (404, 429, offline) the signup moves on and `/register` checks again at the end. The same call brings the CNPJ's standing at the Receita (backend #119, `cnpj_situacao`, off in prod until `CNPJ_CONSULTA_HABILITADA`): `nao_encontrado`/`inativa` block the CNPJ field (and `/register` answers a 422 on `cnpj` told apart only by its `msg`, kept in `ErroBackend.mensagens`); `ativa` with a different `razao_social` stops the step once to offer it, never replacing it; `nao_verificado` or a missing field changes nothing. The backend answers the same 401 for an unknown e-mail and a wrong password, on purpose; the login screen shows one message for both.
- **Google sign-in is real** (backend #73), switched on by `NEXT_PUBLIC_LEDGR_GOOGLE=1` with `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` on the server (`lib/google.ts`); off, the login's Google button stays the demo shortcut. The backend checks the identity: the NextAuth `signIn` callback (`aoVoltarDoGoogle` in `lib/login.ts`) sends `account.id_token` to `POST /login/google` and puts the backend user (its `id`, `empresa_id`, `auth_time`, never Google's `sub`) on the same `user` object NextAuth hands to the `jwt` callback. A 404 (no account) keeps the `id_token` in an httpOnly cookie for its 1 hour and sends the user to `/cadastro/google`, the signup without the access step, which ends in `POST /register/google` and opens the session through the `google-cadastro` Credentials provider (it reads the cookie, never the browser). Other refusals go back to `/login?google=<motivo>`; NextAuth's own errors to `/login?error=`.
- **Password recovery is real** (backend #66). The "Esqueci a senha" card calls `POST /senha/recuperar`, which answers the same 202 whether the e-mail has an account or not, and the e-mail links to `/redefinir-senha#token=...`, which calls `POST /senha/redefinir`. The token rides in the fragment so it never reaches the server logs; the page clears it from the address bar. These, `/login`, `/register` and `/register/verificar` are the calls without a Bearer (`publica: true`). The backend rate-limits them by IP (backend #64), so with `LEDGR_SEGREDO_PROXY` set (same value as the backend's) `requisitar` forwards the browser's IP (`x-real-ip`, else the first `x-forwarded-for`) in `X-Ledgr-IP-Cliente` with the secret in `X-Ledgr-Segredo-Proxy`; without it, the backend sees Vercel's IP and one person's wrong passwords lock everyone out.
- **Extratos lists every file sent** from `GET /extratos` (backend #70), conciliated or not (`listarExtratos`); where a file opens comes from the first page of `/execucoes`, and the reason of each unread line from `GET /extratos/{id}`, only for files that have one.
- **Closing the month is real** (backend #86, `fecharMes`/`reabrirMes` in `acoes.ts`). Fechamentos reads `GET /fechamentos` with the executions; a month's state is its most recent record (`fechado` now, or `reaberto`). A ready month closes with one click; one with pending items keeps "Revisar pendências" as the main path, and "Fechar mesmo assim" sends the close, shows the backend's 409 text and asks for a ressalva. A closed month locks checking, justifying and conciliating again (the backend answers 409): the comparison learns it from `GET /fechamentos?competencia=` (`ConciliacaoEmRodadas.fechamento`), hides those actions and links to Fechamentos to reopen. If `/fechamentos` fails, the screens stay read-only about it instead of guessing. A closed month has a printable report (#117) at `/fechamentos/[competencia]/relatorio`, opened by "Baixar PDF" in a new tab with `?imprimir=1` (it calls `window.print()`, so the PDF is the browser's "Save as PDF", A4 via `@media print` on `.rel-*`): the numbers come from the `resumo` frozen in the closing record, the justified and pending lines from each pair's `GET /conciliacoes/{id}` (`carregarRelatorioDoFechamento`, `fechamentos/relatorio.ts`).
- **Still mocked, because the backend has no endpoint for it:** `/regras`, the subscription, and accepting the bank value on a line. Screens showing backend data hide those write actions instead of pretending to save.
- **Rounds, checks and justifications** (`docs/superpowers/specs/2026-10-02-conciliacao-em-rodadas-design.md`). A conciliation is the bank extrato; each system extrato conciliated with it is a round, derived by `lib/rodadas.ts` from `/execucoes?extrato_banco_id=` (backend #82), which returns only that bank extrato's executions. Checking and justifying a line work in the mock (`registrarDecisaoNoMock`, localStorage). With backend data, the box and "Justificar" turn on by themselves when the items bring the `decisao` key, even `null`: they write through `registrarDecisao` to `POST /conciliacoes/{id}/decisoes` (backend #83) with the `chave` the backend sent, and Fechamentos reads `contagens.justificadas` from `/execucoes`. What still asks for a decision is one rule, `pedeDecisao` in `app/(app)/dashboard/resumo.ts`: diverges and is not justified. Conciliações (`/dashboard`, a work list loaded by `carregarConciliacoes`: the conciliation in progress on top, open ones first), Histórico and the Visão geral's recent activity show one row per bank extrato too, with the round that counts (`porConciliacao` in `app/(app)/historico/execucoes.ts`), grouped page by page; Histórico groups them by the extrato's month like Fechamentos.
- **Approving justifications** (backend #132, front #168; the backend ships it behind `APROVACAO_JUSTIFICATIVAS_HABILITADA`, off in production: with it off a justification is born approved, nothing below shows and the month closes as before). A justification is `pendente` or `aprovada` in `decisao.situacao` (no field counts as aprovada, `estaJustificada`/`aguardaAprovacao` in `lib/aprovacao.ts`); the approver comes in `aprovada_por`/`aprovada_em` (`adaptarDecisao`). A rejection is not a state: the line goes back to divergent with `decisao: null` and the event `justificativa_rejeitada` (with the reason in `texto`) in `eventos`. A pending line is `aguardando` in `situacaoDaLinha`: it stays in "Só revisão" and out of "Justificadas", `pedeDecisao` is still true, and `contagens.justificadas` counts only the approved ones. `aguardando_aprovacao` comes in `GET /conciliacoes/{id}` (root), `GET /execucoes` (`contagens`) and the closing `resumo`, and the month cannot close with any: the 409 carries the number only in its text, and even a ressalva does not release it, so the Fechamentos panel shows a step with "Aprovar as N justificativas" (`POST /justificativas/lote` by `competencia`, `aprovarPendentes`) and hides "Fechar mesmo assim". In the line's window the admin and the gestor approve or reject one (`POST /conciliacoes/{id}/decisoes` with `tipo` `justificativa_aprovada`/`justificativa_rejeitada`); the analista sees that it waits and can still undo. Both refuse the analista with 403 before the backend (`podeFecharMes`). The Central de ajuda says nothing about it yet: write it the day the backend turns the flag on, as with the explanation texts. Not built: rejecting in batch (the route takes `acao: "rejeitar"` and `motivo`) and approving by `itens` from the comparison.
- **The bank extrato's balance** (front #118, backend #118/PR #120): `saldo_inicial`, `saldo_final` and `saldo_data` (decimals in text, or null) in `GET /extratos`, `GET /extratos/{id}` and the root of `GET /conciliacoes/{id}`, read by `adaptarSaldo` in `lib/adaptadores.ts` and shown by `app/(app)/saldo.tsx`: a strip above the summary in the comparison, "Saldo final"/"Data do saldo" in the Extratos panel (bank files only), and the final balance under each pair in Fechamentos (from the bank extrato's detail it already reads). Three states: no keys (a backend before #118) shows nothing; null says "Saldo não informado no arquivo", never R$ 0,00; a final balance with a null initial means unread lines, and the screen says the initial depends on them instead of computing it.
- **The month of a conciliation** is the month of `periodo_inicio` of its BANK extrato (backend #82), which comes in every `/execucoes` item (`Execucao.periodoInicio`) and is the same rule the backend uses to close a month; `competencia()` in `app/(app)/fechamentos/fechamento.ts` falls back to the month it ran when the period is null. Every screen (Fechamentos, Histórico and its chart, Conciliações, the rounds line) uses it, so none opens a conciliation just to learn its first date.
- **The date tolerance is editable** in Configurações › Conciliação, from `GET`/`PUT /empresa/configuracoes` (backend #85, `carregarRegras`/`salvarToleranciaDias`): 0 up to the `tolerancia_dias_maximo` the backend sends, saved by button, valid from the next conciliation. It is the only engine rule the backend keeps (value tolerance and similarity were dropped, ADR-006/008); with a 404 the dialog shows the last conciliation's tolerance, read only.
- **The account comes from `GET /me`** (backend #81), read once per layout load by `contaDaSessao` in `app/(auth)/acoes.ts`: the company name for the header and menu, and whether the account has a password (`metodos_login`; a Google-only account gets no "Trocar senha"). The role comes in `papel` (`admin`, `gestor` or `analista`, backend #133, read by `lerPapel` in `lib/papel.ts`); without it the old `administrador` decides (false is analista), and without both the account is admin, as in the old single account. `administrador` is obsolete on the backend and goes away only after we tell them we stopped reading it.
- **The active company lives in the URL** (backend #133/ADR-019, front #169 part A, `docs/superpowers/specs/2026-10-21-empresa-ativa-na-url-design.md`). Every app screen is `/e/<empresa-uuid>/<screen>` (`app/(app)/e/[empresa]/...`), one scheme even with a single company: the token cookie is shared by every tab, so the active company can't live in it. `proxy.ts` reads the UUID from the path and leaves it in the request as `x-ledgr-empresa` (always deleting any incoming one); `chamarBackend`/`baixarDoBackend` (`lib/backend.ts`) send it as `X-Ledgr-Empresa`, so no Server Action passes it. The CSV route (`/api`, outside the proxy) takes `?empresa=` and passes `{ empresa }` to `baixarDoBackend`. `lib/rotas.ts` holds the pure rules (`comEmpresa`, `caminhoSemEmpresa`, `destinoDaTroca`, `escolherEmpresa`, `destinoDaUrlAntiga`); inside the tree, links, pushes and redirects go through `LinkDoApp` (`lib/link-do-app.tsx`), `useRoteador()` (`lib/roteador.ts`) and `redirecionarNoApp()` (`lib/rotas-servidor.ts`), and `lib/rotas.guarda.test.ts` fails on a raw `Link`, `useRouter`, `redirect` or literal address to an app screen (write new links with the helpers). The layout of `e/[empresa]` checks the UUID against `me.empresas` (404 otherwise; without the list, as on a backend before #133, it accepts it) and gives `ProvedorDaEmpresa` the active company: the screens' header shows it and the user card shows the account. `app/(sem-empresa)/[secao]/[[...resto]]` redirects the old URLs (`/visao-geral`, favourites, the login target) to the last company used (cookie `ledgr-empresa-recente`, a preference only: it never goes to the backend) or the first, and answers 404 to anything that could leave the site. `SeletorDeEmpresa` (top of the sidebar, hidden with one company, search above 8) switches to the same screen in the other company, or to the section root from a screen with an id. Registering companies is the next bullet (a screen of the menu). Not built: the `conta_id` JWT claim (the backend still accepts the old `empresa_id`).
- **Client companies and plan limits** (backend #133 part 2, front #169 part B, `docs/superpowers/specs/2026-10-22-empresas-na-configuracao-design.md`). **Empresas is a screen of the side menu** (`/e/<empresa>/empresas`, `app/(app)/e/[empresa]/empresas/`, between Histórico and Assinatura; `empresas` is in `SECOES`), not a section of Configurações. `page.tsx` is a Server Component like Extratos: it loads `GET /empresas` (everyone; `{ itens }` with `cnpj_verificado_em`) through `carregarEmpresas` and hands the list to `PainelDeEmpresas`, which carries its own `Cabecalho` because the header's button ("Adicionar empresa" or "Convidar pessoa") opens a **modal window** for the active tab (`ModalDaTela`: the same native `<dialog>` with `showModal` as the comparison's, blurred and darkened backdrop, a soft entry `.modal-suave` for those who did not ask for less motion; it closes with Esc, Cancelar/Fechar or a click on the backdrop, and the forms inside keep their rules). **The screen has two tabs, Empresas and Equipe** (decision of 23/10, the team moved here from Configurações): `?aba=equipe` opens on Equipe (`page.tsx` reads `searchParams.aba`; any other value is Empresas), switching tabs does not reload and `replaceState`s the URL, the arrows move between tabs, and the team loads with the screen (`useEquipe`, so the Equipe tab's number and the switch are immediate). The selected tab is read from the browser's URL on the client (`useSearchParams`), not from the server render, so the back button never shows one tab with the other tab's URL; both panels stay in the DOM (`hidden` on the inactive one), so `aria-controls` is valid and what was typed survives a tab switch. The table shows razão social with "Ativa", CNPJ with "CNPJ verificado", the registration day and "Abrir", which goes to the other company's **Visão geral** (cookie + `comEmpresa`; the selector keeps the same screen instead). The admin and the gestor register one (`CadastrarEmpresa`, `cadastrarEmpresa`: the CNPJ goes with letters and digits only, upper case, after `validarCnpj`, which already knows the alphanumeric CNPJ; razão social is not taken from the Receita, the authenticated route does not return it); on success the new company opens on its Visão geral. A double submit sends once (a `ref` locks before the first `await`). The errors: 409 and 422 sit under the CNPJ field (422 is the format or the Receita, from `ErroBackend.mensagens.cnpj` with the `Value error, ` prefix removed), 402 shows the backend's text with "Ver planos" and re-reads the page (`router.refresh()`), 429 reads `Retry-After`, 403 re-reads the page. The analista only sees the list. `limites` of `GET /me` (`{ empresas: { usadas, maximo }, usuarios: { usados, maximo } }`, `maximo` null is unlimited) is read by `adaptarLimites` in `lib/limites.ts`, carried `contaDaSessao` → `Shell` → `ProvedorDaConta` and read with `useLimites()`; without the field nothing is shown. `situacaoDoLimite` gives `livre`, `folga`, `perto` (one left, or 80%), `no-limite` and `acima`, and `textoDoLimite` the sentence. Each tab starts with `FaixaDoPlano` ("3 de 5 empresas", "2 de 3 pessoas", a usage bar only when there is a maximum, red at the limit): in Empresas, at the limit or above it, the add button is off (the backend answers 402 even to the admin); in Equipe the same notice for people (active plus pending invites) only warns, it does not turn the invite off, because re-sending to the same e-mail takes no seat and the screen cannot predict the 402. The selector ends its list with a "Gerenciar empresas" link to the screen; with one company the selector is hidden, so the way in is the menu. The Central de ajuda has an "Empresas" page (cover `public/ajuda/empresas.webp`); the screen has no mascot tutorial yet (Assinatura has none either). Not built: editing or removing a company (no backend route).
- **Team and invites** (backend #69/#73, `docs/superpowers/specs/2026-10-16-equipe-e-convites-design.md`). Three roles (#133): the admin signed the company up; the gestor and the analista come by invite. The **Equipe tab of the Empresas screen** (`app/(app)/e/[empresa]/empresas/painel-da-equipe.tsx`, actions in `equipe/acoes.ts`; it lived in Configurações until 23/10: each person with initials avatar, "você" and the role as a label, pending invites in dashed rows, the invite as a panel with one **card per role** explaining what it allows, the least powerful role preselected, "Remover" asking for confirmation on the row; the signed-in person is marked by `useEmail()` from `ProvedorDaConta`) lists people from `GET /empresa/usuarios` (everyone) and, for the admin and the gestor, pending invites from `GET /empresa/convites` (a 403 there leaves the list without them, it does not break the team), with invite (`POST` with `{ email, papel }`: the admin invites gestor or analista, the gestor only analista; 409/429 with `Retry-After` in `ErroBackend.segundosParaTentar`/503 while the backend's e-mail is off), cancel and remove (cuts access at once). The invite link is `/aceitar-convite#token=...` (`app/(auth)/aceitar-convite/`): the page reads the token from the fragment, clears it, calls `POST /convites/consultar` and accepts with name and password (`POST /convites/aceitar`, then `entrar`) or with Google: "Aceitar com Google" stores the token in the httpOnly cookie `ledgr-convite-google` (1 hour) and `aoVoltarDoGoogle` sees it and calls `POST /convites/aceitar/google` instead of `/login/google`; refusals come back as `/aceitar-convite?google=<motivo>` and the server re-reads the invite from the cookie (`conviteDoCookie`). Someone already signed in sees "Sair e continuar" first. The plan limit for people only warns (see the bullet above). Everybody justifies (decision of 21/10); closing or reopening a month is for the admin and the gestor (`podeFecharMes` in `lib/papel.ts`, text in `lib/gestor.ts`): `ProvedorDaConta` carries `papel` (`usePapel`, `usePodeFechar`), the Fechamentos panel hides those buttons for the analista with a one-line reason, and `fecharMes`/`reabrirMes` refuse with 403 before calling the backend. The lock that counts is the backend's (backend #132/#133), whose 403 maps to the same text. Not built yet: changing a role (`PATCH /empresa/usuarios/{id}`) and transferring the admin (`POST /empresa/admin/transferencia`). Removing people stays with the admin.
- **The ERP's PDF is not accepted** until the backend's spike (#84) decides, by 13/10: the backend answers 400 for anything but `.ofx`/`.csv`. The upload fields and every text that offered "CSV ou PDF" say CSV only; commits `8cddca7` and `0e15b2e` show what to bring back if it returns (system side only).
- **Hidden until the backend has the route:** changing the account e-mail (`POST /me/email`, backend #66). Configurações › Conta shows the e-mail and says to write to support instead; `trocarEmail` stays ready and tested in `app/(auth)/acoes.ts`.
- **Deactivating the account is real** (`DELETE /me`, backend #68, `desativarConta`): Configurações › Conta › "Desativar conta" asks the current password (none for a Google-only account, where the backend checks a recent login and answers 409 otherwise), ends the access, frees the e-mail and signs out. An administrator with other people on the team gets the backend's 409 asking to remove them first. The company's data stays: deleting it is on request ("Excluir os dados da empresa" › "Pedir por e-mail", an internal script on the backend), as the privacy policy says.
- **First use** (`docs/superpowers/specs/2026-10-15-primeiro-uso-design.md`). The signup has three steps (access, company, management system; the bank step is gone) and ends on the Visão geral. Each screen has a mascot tutorial (`app/(app)/tutorial/`, texts in `roteiros.ts`, targets marked with `data-tutorial`), reopened by "Rever o tutorial" in the top bar's Ajuda menu; the Visão geral shows the first-steps roteiro (`visao-geral/roteiro.ts`, data from `carregarRoteiro`) until the first closed month or "Já sei usar". What was dismissed lives in `ProvedorDaConta` (`app/(app)/conta.tsx`): `preferencias` from `GET /me` plus `localStorage`, written to both through `PATCH /me/preferencias`, which the backend may not have yet. The 14-day trial reads `situacao`/`plano`/`teste_termina_em` from `GET /me` (`lib/assinatura.ts`): `sem_plano` sends the app to `/plano` (`POST /empresa/plano`; a guided choice: a slider asks how many entries a month and the card shows the plan for it, over 350 it is "Fale com a gente"; no billing period yet, it comes with the gateway and the partners' discounts, #167), `teste` shows the days left in the top bar, `teste_encerrado` (or a 402 when conciliating) swaps the new conciliation for the plans. **Without those fields nothing blocks**, so production keeps working until the backend ships them. "Tolerância revisada" needs nothing new: `atualizado_em` of `/empresa/configuracoes` is null before the first change.
- **Help is front-only** (#171, `docs/superpowers/specs/2026-10-20-central-de-ajuda-design.md`). The top bar's "Ajuda" button (`app/(app)/ajuda/menu-de-ajuda.tsx`) opens a menu: "Ajuda desta tela" (a side panel, `painel-de-ajuda.tsx`, listing the screen's features with links to `/ajuda/<pagina>#<funcao>`), "Rever o tutorial" and the Central de ajuda (`/ajuda/[pagina]`). The Central is a separate system in its own route group, `app/(ajuda)/`: full screen, without the app menu and top bar, behind the same login check, with one exit, "Voltar ao Ledgr", back to the screen it was opened from (`ajuda/voltar.ts`, sessionStorage, same-site paths only; else the Visão geral). It has one page per app screen, in menu order, each listing ALL its features (what it does, how to do it, a note), with the screens on the left, the text in the center and "Nesta página" on the right; written in `app/(ajuda)/ajuda/paginas.ts` (`**negrito**` marks button names), no editor. Pictures are screenshots of the app with the test account in `public/ajuda/` (each with its size, so the space is reserved and anchor scrolling lands right); a page gets a video only when `video` points to a file there, otherwise the cover says "Vídeo desta tela em breve".
- `lib/mock-data.ts` still backs everything in the list above. When a real endpoint shows up, the swap point is named in a `ponytail:` comment next to the mock call.
